## 1. Cover Page

This report documents the design, implementation, and local verification of MetaGuard, an isolated metadata-protection teaching lab. All endpoints are local and all metadata/credential values are synthetic.

## 2. Abstract

Server-Side Request Forgery (SSRF) can cause a server to send requests to destinations chosen by an attacker. In cloud environments, metadata endpoints may disclose instance details or temporary credentials. MetaGuard demonstrates a defensive request path using short-lived tokens, HTTP method and metadata resource validation, destination restrictions, SSRF indicator detection, SQLite security events, and an interactive dashboard. The implementation uses a mock provider and never makes an outbound request. Test results are generated by the local API and recorded in SQLite.

## 3. Introduction

Cloud workloads often expose a metadata interface to obtain instance configuration and workload identity. If an application can be induced to request attacker-controlled URLs, metadata endpoints can become an unintended target. This project makes the security decision visible and testable without using a cloud account or real credentials.

## 4. Problem Statement

An application that accepts untrusted destination or path input may become a server-side request proxy. If metadata endpoints are reachable from that server, a successful SSRF can disclose sensitive workload data. Defenses should constrain destinations and resources, require appropriate authentication, reject unnecessary methods, and produce useful audit records.

## 5. Objectives

- Build a real Flask API with a local mock metadata provider.
- Demonstrate a short-lived IMDSv2-style token workflow.
- Enforce method, destination, path, and token policies in backend code.
- Log decisions to SQLite and expose metrics/search APIs.
- Build a React SOC dashboard that consumes backend responses.
- Execute and save reproducible positive and negative test cases.
- Package a local-only Docker Compose workflow and user documentation.

## 6. Scope

Included: local dummy metadata, Flask routes, policy checks, token expiry, SQLite logs/rules/test history, a React dashboard, Pytest, Docker files, documentation, and presentation assets. Excluded: real cloud metadata endpoints, real credentials, production forwarding, cloud deployment, user accounts, and multi-instance state.

## 7. SSRF Explanation

SSRF is a class of vulnerability where an attacker influences a server to make a request to an unintended destination. Risk depends on server network reachability and what the target returns. Mitigations include destination allowlists, strict parsing, avoiding arbitrary URL fetches, network egress controls, and treating metadata access as privileged.

## 8. Cloud Metadata Services

Cloud platforms provide metadata interfaces for machine identity and instance configuration. These may expose identifiers, network configuration, identity/role information, or temporary credentials. The exact endpoint and controls vary by provider. This lab uses only a local mock and makes no claims that it reproduces every provider behavior.

## 9. IMDSv2 Explanation

AWS EC2 Instance Metadata Service v2 uses a session-token workflow: a client obtains a token and includes it in subsequent metadata requests. This helps mitigate some SSRF paths that cannot perform the required token acquisition. MetaGuard demonstrates the pattern with a local token issued via PUT, configurable expiry, and a required token header on protected reads. It is an educational approximation, not an AWS implementation.

## 10. Proposed Solution

The Flask proxy accepts an allowlisted metadata resource, checks the request method, optional destination hint, path, and token, then reads from fixed in-process mock data. It never uses the supplied destination to open a connection. Decisions are persisted and presented through the React UI.

## 11. Architecture

See [`architecture.md`](architecture.md) for a component diagram, data model, request order, and trust boundaries. In summary: React/Vite → Flask policy/API → in-process dummy metadata provider; Flask records events, rules, and saved test executions in SQLite.

## 12. Functional Requirements

The application issues expiring tokens; serves safe mock instance data; rejects missing/invalid/expired tokens, invalid methods, disallowed resources and destinations; records source/path/method/reason/severity/result/timestamp; displays backend metrics and searchable events; supports CSV export and confirmed lab-data clearing; exposes configurable rule switches; and stores test execution results for review.

## 13. Non-functional Requirements

The system should run locally on Windows or Docker, default to loopback exposure, avoid production credentials, provide understandable policy output, persist audit data, and remain usable on desktop and small screens. It is not designed for production availability or multi-user access.

## 14. Implementation

The backend is Flask with SQLite. Tokens are generated from cryptographically secure random bytes and stored in process memory with expiry timestamps. Metadata paths are exact allowlisted strings. The dashboard calls REST endpoints for metrics, event records, rule state, configuration, and test history. The frontend has no hardcoded security statistics; overview counts and chart data come from SQLite queries.

## 15. Security Controls

- Secure default: tokens, method restriction, destination allowlist, path validation, and SSRF detection are enabled.
- The default native API bind is `127.0.0.1`; Compose host ports bind to loopback.
- CORS is restricted to local development origins by default.
- No HTTP client or URL fetch is used for proxy requests.
- The metadata mock is separately token-protected.
- Credential-like values are conspicuously synthetic and non-functional.
- Search parameters are bounded and SQL statements use placeholders.
- Rule toggles are for local learning only. Disabling rules is not an authenticated administrative workflow.

## 16. Testing Methodology

Pytest uses a temporary SQLite database per test fixture and Flask's test client. Tests cover token issue/TTL/expiry, missing/invalid/expired tokens, accepted mock reads, direct mock protection, unauthorized paths and destinations, invalid methods, SSRF event severity, overview/event filtering, saved test reports, policy toggles, config, and clearing. The in-app suite invokes the real Flask route handlers through a test client and persists every batch.

## 19. Limitations

Tokens are in-memory and disappear on restart; SQLite is a single-instance store. There is no user/admin authentication, TLS, distributed token service, provider SDK, production egress firewall, or real cloud integration. SSRF detection is a teaching policy, not a complete URL/IP parser or substitute for network controls. A destination supplied in the UI is never contacted.

## 20. Future Enhancements

Potential follow-ups include authenticated policy administration, role-based access, structured alert export, request correlation IDs, stronger deployment hardening, integration tests against containerized services, and optional synthetic traffic generation. Any actual cloud integration would need isolated credentials, explicit authorization, egress controls, and a separate security assessment.

## 21. Conclusion

MetaGuard demonstrates a complete local request validation and monitoring path: token acquisition, guarded metadata reads, deliberate denial cases, event persistence, dashboard review, and automated verification. Its principal safety property is that all metadata comes from a fixed mock provider and no supplied URL is fetched.
